# Contributing to BookMeSilly

Thank you for your interest in contributing to BookMeSilly! This document provides guidelines and instructions for contributing to the project.

## Getting Started

### Prerequisites
- **Git**: Version control
- **Docker**: For containerized builds and testing
- **CMake**: Version 3.10 or later
- **C++ Compiler**: Supporting C++17 standard
- **Qt6 Development Libraries**: For GUI development

### Setting Up Your Development Environment

1. **Clone the repository:**
   ```bash
   git clone https://github.com/yourusername/BookMeSilly.git
   cd BookMeSilly
   ```

2. **Install dependencies:**
   See [docs/setup/DEPENDENCIES.md](./setup/DEPENDENCIES.md) for detailed installation instructions.

3. **Verify the setup:**
   ```bash
   ./scripts/ci/ci-test.sh
   ```

## Development Workflow

### 1. Create a Feature Branch
```bash
git checkout -b feature/your-feature-name
```

Use descriptive branch names:
- `feature/audio-playback` for new features
- `fix/crash-on-empty-library` for bug fixes
- `docs/update-architecture` for documentation
- `chore/upgrade-dependencies` for dependencies

### 2. Make Your Changes

#### Code Style
- Follow C++17 best practices
- Use meaningful variable and function names
- Keep functions focused and small
- Add comments for complex logic

#### Source Code Organization
- **Backend logic**: `src/backend/` and `include/backend/`
- **Frontend UI**: `src/frontend/` and `include/frontend/`
- **Headers**: Corresponding headers in `include/`

#### Testing
- Write unit tests for new functionality in `tests/unit/`
- Ensure all tests pass:
  ```bash
  ./scripts/ci/ci-test.sh
  ```

### 3. Code Quality

#### Static Analysis
Before committing, run cppcheck:
```bash
make run-code-quality
# or
./scripts/analysis/run-code-quality.sh
```

Fix any warnings. If suppression is needed:
1. Use inline `// cppcheck-suppress warning-type` comments in source code
2. Or add pattern-based rules to `config/cppcheck/suppressions.txt`

#### Security Scanning
Check for vulnerabilities:
```bash
make run-security-scan
# or
./scripts/analysis/run-security-scan.sh
```

### 4. Commit Your Changes
```bash
git add .
git commit -m "feat: add audio playback functionality

- Implement audio stream decoding
- Add playback controls
- Update tests for new features

Fixes #123"
```

**Commit message guidelines:**
- Use present tense: "add feature" not "added feature"
- Use imperative mood: "move cursor to..." not "moves cursor to..."
- Limit the first line to 70 characters
- Reference issues and pull requests when appropriate
- Separate subject from body with a blank line

### 5. Local Testing

Run the complete CI pipeline locally:
```bash
./scripts/ci/ci-test.sh
```

This verifies:
- ✓ Docker images build successfully
- ✓ All unit tests pass
- ✓ Production binaries are present
- ✓ No build errors or warnings

### 6. Push and Create a Pull Request
```bash
git push origin feature/your-feature-name
```

Then create a Pull Request (PR) on GitHub with:
- Clear title describing the change
- Detailed description of what was changed and why
- Reference to any related issues
- Screenshots for UI changes

## Pull Request Guidelines

### What We Look For
1. **Code Quality**
   - Follows the code style and conventions
   - No cppcheck or security warnings
   - Tests pass and coverage is maintained

2. **Documentation**
   - Code comments explain complex logic
   - README updated if needed
   - Architecture docs updated for major changes

3. **Testing**
   - New features have corresponding tests
   - Existing tests still pass
   - Edge cases are covered

### Review Process
- At least one maintainer will review your PR
- Feedback will be provided constructively
- Address feedback by pushing additional commits
- PR will be merged once approved

## Reporting Issues

### Bug Reports
Include:
- Detailed description of the issue
- Steps to reproduce
- Expected vs actual behavior
- Environment (OS, Docker version, etc.)
- Relevant logs or error messages

### Feature Requests
Describe:
- The desired functionality
- Use cases and benefits
- Any relevant implementation notes

## Project Structure

See [docs/ARCHITECTURE.md](./ARCHITECTURE.md) for detailed project organization. Key locations:

- **Source code**: `src/` and `include/`
- **Tests**: `tests/`
- **Documentation**: `docs/`
- **Configuration**: `config/`
- **Scripts**: `scripts/`
- **Build output**: `build/` (generated by CMake)

## Documentation

Good documentation helps everyone! You can contribute by:
- Improving existing docs in `docs/`
- Adding clarifying comments to code
- Creating guides for common tasks
- Reporting documentation gaps

## Code Review Checklist

Before submitting a PR, ensure:
- [ ] Branched from `main`
- [ ] Commits are logical and well-described
- [ ] Code follows project style
- [ ] All tests pass: `./scripts/ci/ci-test.sh`
- [ ] Static analysis passes: `make run-code-quality`
- [ ] Security scan passes: `make run-security-scan`
- [ ] Documentation is up-to-date
- [ ] No large unrelated changes in the same PR

## Questions?

- Check existing issues and discussions
- Review [docs/ARCHITECTURE.md](./ARCHITECTURE.md)

- Open a discussion on GitHub
